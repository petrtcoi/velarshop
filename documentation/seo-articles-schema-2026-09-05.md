# ТЗ на Schema.org для трех статей VelarShop

## Общая логика

Для каждой новой страницы одновременно выводить `Article` и `FAQPage` в JSON-LD. Разметка должна формироваться серверным шаблоном из frontmatter статьи, а не вставляться вручную в MDX. Канонический URL должен совпадать с конечным адресом страницы и не вести через редирект. Все данные в разметке должны быть видимы пользователю на странице.

## Article

Обязательные поля:

- `@context`: `https://schema.org`;
- `@type`: `Article`;
- `headline`: точный H1 статьи;
- `description`: `metaDescription`, при его отсутствии `short_description`;
- `mainEntityOfPage`: абсолютный канонический URL;
- `url`: абсолютный канонический URL;
- `image`: абсолютный URL главного WebP-изображения;
- `datePublished`: дата первой публикации в ISO-формате;
- `dateModified`: дата последнего содержательного изменения в ISO-формате;
- `author`: организация `VelarShop`;
- `publisher`: организация `VelarShop`;
- `inLanguage`: `ru-RU`.

В текущем проекте эта схема уже строится общей функцией `buildArticleJsonLd`. Для новых материалов все необходимые значения передаются через frontmatter. После сборки нужно проверить, что `headline`, `description`, канонический URL и изображение относятся к той же статье.

## FAQPage

Для каждой статьи использовать пять вопросов, которые одновременно находятся в frontmatter `faq` и видимой секции `## Частые вопросы`. Каждый вопрос размечать как `Question`, а ответ - как `Answer` в поле `acceptedAnswer`. Текст в JSON-LD должен совпадать по смыслу с видимым ответом и не содержать скрытых коммерческих обещаний, цен или условий, которых нет на странице. FAQPage выводить только при наличии массива `faq`, чтобы не создавать пустую схему.

Рекомендуемые вопросы уже добавлены в статьи:

- для трубчатых радиаторов в интерьере - место, размер, цвет, ориентация и данные для подбора;
- для радиатора в спальне - тип, место, термостат, шум и установка рядом с кроватью;
- для покрытия - практичность, теплоотдача, различие RAL, самостоятельная перекраска и уход.

В текущем проекте FAQPage уже генерируется общей функцией `buildFaqPageJsonLd`. Дополнительный ручной `<script type="application/ld+json">` внутри статей не нужен, иначе на странице появятся дублирующиеся сущности.

## Проверка перед публикацией

После `npm run build` проверить конечный HTML каждой страницы. На каждой странице должны быть одна сущность `Article`, одна сущность `FAQPage`, один H1 и видимые ответы на все вопросы. Затем проверить JSON-LD штатным валидатором проекта и Rich Results Test. Ошибки структуры, несовпадение URL, отсутствующее изображение или невалидная дата блокируют публикацию до исправления.
